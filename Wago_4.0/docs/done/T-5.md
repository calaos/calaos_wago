# T-5 — `lights[]` est trop court d'un octet pour la dernière règle

**Statut** : ✅ clos le 2026-09-14 · **Type** : fix · **Commit** : `0fa011c`

> Corrigé par l'option 1 du §4 : `lights` devient un `ARRAY[0..64]`. Le §5 tombe de lui-même —
> ni `ManageOutput` ni `SeedOutputState` n'ont eu à bouger, c'est le tableau sous-jacent qui
> s'élargit sous les deux. Relecture `codesys-review` : CONFORME.

---

## 1. Un tableau de 64 octets pour 513 règles

`src/targets/881/VARIABLES_GLOBALES.EXP` déclare, d'un côté, les règles sur **513 entrées** :

```pascal
event:       ARRAY[0..512] OF INTER_EVENT;   (* l.27 *)
volets:      ARRAY[0..512] OF VOLET;         (* l.30 *)
output_type: ARRAY[0..512] OF OUTPUT_TYPE;   (* l.84 *)
output_addr: ARRAY[0..512] OF OUTPUT_ADDR;   (* l.85 *)
```

et de l'autre l'état des télérupteurs sur **64 octets** :

```pascal
lights: ARRAY[0..63] OF BYTE;   (* l.28 *)
        (* MAX of 256/8 = 32 digital output modules as lights *)
```

L'indexation est `lights[tmp / 8]`, bit `tmp MOD 8`, où `tmp` est un **id de règle**
(`MANAGEOUTPUT.EXP:28-29, 34, 36`, et les blocs suivants). 64 octets couvrent donc les ids **0 à
511**.

## 2. La règle 512 écrit un octet au-delà du tableau

`ManageOutput` balaie `FOR cpt := 0 TO 512` (`MANAGEOUTPUT.EXP:18`). Pour `tmp = 512` :

```
512 / 8 = 64   →   lights[64]   sur un ARRAY[0..63]
```

⇒ dépassement de **exactement un octet**, en lecture (`SHR(lights[tmp / 8], …)`) comme en écriture
(`lights[tmp / 8] := lights[tmp / 8] OR SHL(BYTE#1, tmp MOD 8)`).

⚠️ **La portée est étroite, et il faut le dire** : seul l'id de règle **512** est concerné. `511 / 8`
vaut 63, dans les bornes. Ce n'est donc pas « l'indexation est fausse », c'est « il manque un octet
pour la toute dernière règle ». Le défaut ne se manifeste que si une règle d'id 512 existe **et** est
de type `TELERUPTEUR` (ou `TELERUPTEUR_DALI` / `_DALI_GROUP`, qui utilisent le même tableau).

## 3. Pourquoi ça ne se voit pas

CoDeSys 2.3 ne contrôle pas les bornes de tableau à l'exécution et n'émet aucun diagnostic à la
compilation ici. L'écriture va silencieusement dans l'octet qui suit `lights` en mémoire — la
variable voisine dans la GVL. Aucune erreur, aucun log : une corruption muette.

## 4. Deux correctifs possibles, à trancher

1. **Agrandir** : `lights: ARRAY[0..64] OF BYTE;`. Cohérent avec les autres tableaux, aucun autre
   changement. ⚠️ `Variables_Globales` est **spécifique à la cible** (3 variantes) : il faut modifier
   les 7 fichiers `src/targets/<cible>/VARIABLES_GLOBALES.EXP`.
2. **Borner la boucle** : `FOR cpt := 0 TO 511` dans `ManageOutput`. Plus court, mais cela retire une
   règle au système et désaligne `ManageOutput` des quatre tableaux déclarés `0..512`.

Le commentaire d'origine (« MAX of 256/8 = 32 digital output modules ») suggère que l'auteur pensait
à 256 règles, pas 513 : les tableaux `0..512` ont grandi, `lights` non. L'option 1 est celle qui
recolle à l'intention apparente, mais le choix appartient au mainteneur.

## 5. ⭐ Le correctif T-2 reproduit ce défaut, délibérément

Le POU `src/common/SEEDOUTPUTSTATE.EXP` ajouté par T-2 balaie lui aussi `FOR cpt := 0 TO 512` et
indexe `lights[tmp / 8]` à l'identique. C'est **voulu** : il devait rester en phase avec
`ManageOutput`, et diverger aurait créé une incohérence pire que le défaut. Il n'ouvre donc aucun cas
de défaillance nouveau, mais il faudra le corriger **en même temps** que `ManageOutput`, sans quoi
les deux ne parleront plus du même tableau.

## 6. ⛔ Le nu

Lu, compilé, jamais exécuté. Les déclarations, la borne de boucle et l'expression d'indexation sont
lues dans le source `.exp` exporté du `.pro` : texte fiable, numéros de ligne fiables. Le
dépassement est **déduit de l'arithmétique** `512 / 8 = 64 > 63`, il n'a **pas été observé** : rien
n'a été exécuté sur automate, aucune corruption n'a été constatée. On ne sait pas non plus si une
règle d'id 512 existe dans une configuration réelle — c'est ce qui décide si le défaut est atteint ou
seulement atteignable.
